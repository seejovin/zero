# Security model — Android 0.10.0 source / web 0.6.0

## Scope and assurance

The Android source enables nine reviewed mainnets and 24 fixed asset/network positions. [NETWORK_EXPANSION.md](NETWORK_EXPANSION.md) is the authoritative current matrix. This is a source candidate, not a newly compiled APK; delivered Android0.8.0 and web0.6.0 remain unchanged. This update was not independently audited and no live funds were moved.

The encrypted entropy vault, BIP-39 passphrase policy and EVM derivation path are unchanged. Solana derives `m/44'/501'/0'/0'` through SLIP-0010 Ed25519. TRON derives `m/44'/195'/0'/0/0` through BIP-32 secp256k1. Secrets stay within the existing authenticated vault/signing boundary; new address exports contain public addresses only.

Seven EVM networks use restricted type-2 native/ERC-20 transfer encoding. Solana permits System transfers, fixed classic-SPL TransferChecked instructions and required associated-token-account creation. TRON permits only local canonical TransferContract/official USDT transfer TriggerSmartContract construction. Remote opaque transaction blobs cannot become approved signing instructions. No arbitrary hash/message signing, approvals, swaps, bridges, permission changes or dApp capability is added.

EVM schema4 is used only for new journals; schema2/3 retain their existing constraints and bytes. Solana/TRON use separate network/address-bound append-only journals. Exact prepared and signed payloads are revalidated during replay. One unresolved outgoing intent per family/network blocks another; expiry prevents stale submission but does not establish non-execution. A signed transaction is never automatically rebuilt with a new blockhash, TAPOS reference, timestamp or signature. Contradictory finality/credit evidence remains a discrepancy and blocks unsafe continuation.

TronGrid API credentials, if configured by the user, are stored under a separate Android Keystore AES-GCM key and no-backup file. They are sent only as a header to the fixed HTTPS TronGrid origin, with redirects rejected. Credentials are not wallet keys. TronGrid may reject unauthenticated requests; current provider availability has not been established for this candidate. Source access and software-distribution trust remain relevant even without a custody service.

The product has no custody backend, cloud recovery, merchant ledger, trading engine, smart account or generic dApp signer. Blockchain providers can observe public addresses/transactions and Coinbase can observe requested asset price pairs. The wallet is not a consensus-verifying light client: TLS, chain identity and internally consistent receipt/block evidence still depend on provider honesty.

## Trust boundaries

| Boundary | Implemented control | Trust that remains |
| --- | --- | --- |
| Recovery entropy | 256 bits from OS/browser cryptographic randomness; 24 English BIP39 words; standard BIP32 derivation | Device/browser randomness and dependency implementations |
| Signing policy | Restricted EVM type-2 native/ERC-20, Solana transfer/SPL, or TRON transfer protobuf; reconstruct and validate reviewed bytes before signing | Executing application, displayed review, Rust dependencies and operating system |
| Entropy vault | Versioned AES-256-GCM ciphertext with fresh 96-bit nonce and authenticated context | Vault-key secrecy; authenticated encryption cannot protect an already unlocked, compromised process |
| Android vault key | Random 32-byte vault key always encrypted under Android Keystore; optional per-use device authentication or 6-digit app PIN envelope; account/alias/policy bound as authenticated data | Selected lock mode, Keystore implementation, device integrity and application process |
| Web vault key | Random 256-bit core credential encrypted under a non-extractable WebCrypto key; optional 6-digit PIN adds an Argon2id/AES-GCM inner envelope and durable attempt limits | Browser profile and OS integrity, selected app lock, extensions and every script served by the wallet origin; non-extractability is not hardware isolation |
| Native evidence | SQLite WAL, synchronous FULL, append-only events, immutable identity and transaction fields, database bound to chain and address | Local filesystem and OS durability; not tamper-proof against full device control |
| Browser evidence | IndexedDB strict-durability transactions, unique account/network/nonce reservation, revision checks, append-only application event API | Browser persistence, origin storage and application code; scripts with the same origin can alter IndexedDB |
| Network evidence | Fixed provider allowlists, with EVM/Solana read fallbacks and TronGrid access configuration, chain checks before fallback use, bounded duplicate-rejecting JSON, block-pinned observations and shared receipt validation | Provider honesty, availability, finality reporting and Base's infrastructure; fallback is not a consensus quorum |
| Android USD valuation | Fixed HTTPS Coinbase public spot endpoints for supported symbols, no redirects or credentials, bounded strict responses with one timeout-only retry, exact decimal valuation, receipt-time freshness and separate price worker | Coinbase pricing/availability, TLS and device clock; indicative prices do not authorize a transaction |
| Software delivery | Pinned dependencies/toolchain, lockfiles, restricted interfaces and validation evidence | Developer machine, source review, CI, signing credentials, hosting administration and distribution |

### Android-specific boundary

The Keystore protects the wrapping key. All asset-family signing still runs in software: after the selected protection is opened, the unwrapped vault key, seed derivation material and signing key temporarily enter application memory. This is not an external hardware signer or a claim that signing keys never enter RAM. Hardware-backed Keystore capabilities depend on the device; this implementation does not require or attest a particular hardware security level.

Wallet files are stored under the application's no-backup directory, with private file permissions, atomic manifest writes and file/directory synchronization. Platform backup is disabled. Each network has a separate SQLite journal. When selected, device authentication authorizes the specific cipher operation. The 6-digit app-PIN mode uses PBKDF2-HMAC-SHA256 (600,000 rounds with fresh salt) to encrypt an inner vault-key envelope, then encrypts that envelope under Keystore. Off still retains Keystore encryption but adds no app-authentication prompt. All modes derive and check the account after opening; an app PIN is not merely a UI boolean. Reopening an encrypted vault derives its address and checks it against the stored receiving address.

The recovery words remain necessary after loss of a device, app data, or its usable Keystore key. A copied encrypted manifest alone is not a portable recovery backup.

Android 0.7.0 creates the wallet before asking the user to record a backup. Success requires an atomic save and matching read-back of the manifest. Backup metadata is retained but no longer blocks startup or sending; removing the onboarding gate does not manufacture confirmation. An interrupted or unverified save retains the wrapping key and existing wallet files rather than overwriting or regenerating them. The operator receives no wallet secrets and cannot recover lost keys. That statement does not mean that blockchain activity or network-request metadata is private.

When the app backgrounds, recovery buffers and sensitive views are cleared. An allowlisted public route may be restored after foregrounding and the selected optional lock, so the user returns to Recovery phrase rather than Home. Words remain concealed until a new explicit reveal. The saved route contains only its wallet identity and supported screen/asset/network identifiers, never recovery words, a PIN, an unwrapped key or payment approval. A prior prepared review returns to Activity, where its existing unsigned intent can be explicitly cancelled before a fresh review. An unprepared fee preview returns to Send.

Android 0.7.1 groups the action selector by the three canonical supported assets, with a separate explicit network choice. Grouping does not combine spendable balances or infer identity from an arbitrary token ticker. Network resolution validates the allowlisted contract and decimals. An unselected network remains unselected in restored public navigation. Changing selection rebuilds the transfer or deposit screen, invalidates old page-bound callbacks and quotes, and selects a draft by wallet, asset and chain. A prepared payment keeps its immutable network binding and durable intent; a navigation change does not authorize another network or silently replace a reservation.

Android 0.8.0 binds every inline withdrawal quote to an immutable, normalized draft and a monotonic request revision/freshness window. Only read-only preview and Max calls may run on the dedicated quote executor. Each creates its own network client; durable repository methods remain serialized on the transaction worker. A bounded pending slot coalesces edits, and page/wallet/foreground checks reject stale completions. A quote grants no signing authority and reserves no nonce. Review can claim the accepted quote for preparation once; final confirmation independently revalidates the resulting immutable prepared transaction. Editing a prepared review requires successful cancellation of the exact unsigned intent. A signed transaction or an uncertain submission cannot be converted back into an editable draft by this path.

The withdrawal form distinguishes the recipient's exact asset amount, the current estimated network fee, the reviewed fee reserve/budget and the eventual receipt fee. ETH is reserved separately for token transfers; no exchange withdrawal charge is deducted from the USDC/EURC amount. USD values remain display-only. A positive fee below one cent is displayed as less than $0.01, not zero. Base's full fee may include execution, L1 data and operator components; a reserve is not an on-chain cap on the additional components. See the [Base fee specification](https://docs.base.org/specifications/transactions/network-fees) and [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559).

### Web-specific boundary

The browser downloads executable wallet code from its origin. **A compromised host, deployment credential, malicious update, browser extension or browser can steal the password/words or change a transaction review.** AES encryption at rest, WASM, a worker, HTTPS and Content Security Policy do not remove this trust. WASM is a shared implementation boundary, not a trusted signing device separated from the page.

A fresh worker performs each protected operation and is terminated afterward. The worker derives the password key locally, checks vault/address identity, and clears mutable key buffers. Rust zeroizes password/key/entropy buffers where owned, including the full Argon2 working allocation. JavaScript strings, generated bridge buffers, allocator copies, screenshots, operating-system copies and a compromised live process prevent a guarantee of perfect erasure.

Encrypted vault material persists locally; the implemented code sends no password, seed, recovery words or vault key to an RPC or application server. Hosted mode uses an explicitly configured same-origin relay for bounded, allowlisted public-chain queries and signed transaction submission. It is not a key service. Static deployments without relay configuration use the fixed HTTPS providers directly. The relay and upstream providers can observe public account queries and signed transactions; they do not receive vault secrets. Legacy password-protected vaults retain their old protection until an explicit authenticated settings change. That change preserves the same recovery words and account, and re-encrypts the core vault with a random credential. Clearing site data, browser eviction or losing app-lock access requires recovery words. Browser persistence is not a cloud recovery service.

## Optional lock and recovery-copy policy (0.5.0)

New wallets default to **App lock: Off** as requested. The secret remains encrypted locally, but anyone able to use the app or browser profile can open it and confirm transfers. Optional protection lives in **Profile → Settings**: fixed **6-digit app PIN**, or Android biometrics/device screen lock. The web version explicitly marks biometric protection unavailable; it does not substitute a UI-only biometric success signal for encryption.

On web, the managed vault and its WebCrypto key/wrapper commit in one IndexedDB transaction. Missing or mismatched pairs fail closed. A PIN wraps the random core credential with Argon2id and AES-GCM inside the device-key wrapper. PIN failures are reserved before decrypting and backed by persistent delay/counter state. The policy, revision and account binding are authenticated; lock changes use compare-and-swap against saved state. Reads revalidate policy after authentication; signing and submission re-check the captured policy independently of BroadcastChannel notification. Browser-profile rollback or malicious same-origin code can bypass client-controlled attempt limits and remains outside the protection promise.

Native changes wrap the same random vault key under a new Keystore alias and commit the manifest atomically. Old v1 device-authenticated vaults keep that mode until explicitly changed. Old wrapping keys are removed only after the replacement is durably committed. Incomplete backup state does not permit creation over an existing wallet: restart resumes the saved account and words.

Copying and screenshots of recovery words are intentionally enabled. Android marks its recovery clipboard entry sensitive and uses bounded cleanup; the browser copies only on a user's action and does not promise clipboard-history erasure. Android permits capture only while the recovery words are displayed, clears sensitive views on background, and otherwise retains the secure-window flag. Clipboard managers, photo backups, cloud sync and anyone holding a screenshot can obtain the recovery secret. The app cannot recall or secure those external copies. These are explicit user-selected tradeoffs, not equivalent to the prior capture prohibition.

## Restricted transaction authorization

- A token is identified by **chain ID and fixed contract address**, never a remotely supplied symbol, image or name. The current registry is defined in NETWORK_EXPANSION.md; bridged lookalikes are not accepted under native token identities.
- There is no arbitrary message/hash/calldata signing, token approval, `permit`, contract deployment, account delegation, upgrade, swap or bridge API.
- The core validates nonzero sender/recipient, EIP-55 mixed-case checksums, exact integer amounts, decimal precision, nonce range, gas range, fee range, supported operation, canonical RLP and low-S signature encoding.
- Payment review binds intent, sender, chain, recipient, asset/contract, exact amount, nonce, gas/fee fields, additional Base fee quotes, timestamps and unsigned bytes. The core rebuilds the preparation before signing. A changed quote cannot reuse approval even when the on-chain unsigned bytes are unchanged.
- Approval expires after five minutes. Signing checks freshness before and after derivation. Expiry does **not** revoke a signature already produced, and a local lock does not cancel a transaction already submitted.
- Client preflight checks chain identity, sender code/delegation at canonical and pending state, nonce consistency, supported token code, balances, transfer simulation and gas. Fresh preflight precedes authentication/signing. Failed prerequisite reads block sending.
- Android binds asynchronous quotes and pre-authentication review checks to the current wallet, page, session and foreground generation. A pause invalidates those callbacks even without `onStop`. Key operations capture their own generation after the authorized device prompt and recheck it before/after unwrap and throughout signing/submission; a later pause/resume cannot revive the scheduled operation.
- The client permits one unresolved outgoing payment per account/network. It cannot prevent account activity from another wallet. Restoring words does not revoke old approvals or delegations created elsewhere.

Recovery derives the first supported account in each family: EVM at `m/44'/60'/0'/0/0`, Solana at `m/44'/501'/0'/0'`, and TRON at `m/44'/195'/0'/0/0`, with an empty BIP39 passphrase. Standard valid English 12/15/18/21/24-word phrases can be restored. Other account indexes, nonempty BIP39 passphrases, imported raw keys and automatic account discovery are outside this version.

## Fees: execution cap and network-specific rollup charges

Android Max uses full integer token units. USDC/EURC Max selects the complete observed token balance; ETH Max subtracts the exact reviewed reserve and simulates the resulting value. Recipient contracts whose gas depends on value are re-simulated until the amount and reserve agree, with a bounded fail-closed calculation. Max preview does not create an intent, reserve a nonce, open a key or broadcast. The preparation step checks draft identity/freshness and recomputes Max before creating the immutable review. Signing never silently replaces the reviewed amount. Base estimates and EIP-1559 fee refunds can leave ETH after a Max transfer; no zero-residual guarantee is made.

The signed EIP-1559 execution cap is:

`max_fee_wei = gas_limit × max_fee_per_gas`

Ethereum receipt fee is `gasUsed × effectiveGasPrice`. Arbitrum One uses that same receipt multiplication with L1 posting already included in its charged gas; adding a separate L1 fee would double-count. Base and OP Mainnet receipt total is:

`actual_fee_wei = gasUsed × effectiveGasPrice + l1Fee + operatorFee`

Base and OP Mainnet L1/operator fees are **not capped by EIP-1559's execution fee cap**. The client quotes `getL1FeeUpperBound(1024)` and `getOperatorFee(gas_limit)` on the fixed GasPriceOracle of the selected chain and reviews:

- In the durable preparation, `estimated_total_fee_wei = max_fee_wei + l1_quote + operator_quote`.
- `fee_reserve_wei = max_fee_wei + 2 × (l1_quote + operator_quote)`.

These are an estimate and a local budgeting buffer, not guaranteed protocol limits. The web draft preview separately shows an expected execution estimate from estimated gas and current base/priority fees, plus the additional Base quotes. If the exact transfer cannot be simulated, it labels a conservative gas assumption and any funding shortage. A preview never reserves a nonce, creates an intent, signs or broadcasts. Network/fee observations are still required; a failed read is not replaced with a fabricated zero. Full preparation and signing continue to require a successful transfer simulation and real affordability checks. Signed transaction bytes are limited to 1024 bytes. Preflight checks current quotes against the reviewed reserve and verifies ETH affordability; excess requires another review. Future Base fee changes can still exceed a quote or reserve.

OP Stack reconciliation requires actual L1 and operator charges. If the operator field is absent, the client queries the oracle using actual gas used at the receipt's canonical block and checks any supplied field against that result. Missing fees are never silently treated as zero. The validator bounds **execution** charges by signed execution terms and adds all components with overflow checks. Additional charges above estimates set a discrepancy flag while preserving the observed success/failure and inclusion/finality. Reverted transactions retain their network charges.

Arbitrum's `eth_estimateGas` includes L1 posting gas. The Android fee fallback therefore never assumes a plain 21,000-gas ETH transfer on that chain. Successful simulation, sufficient ETH and the existing 300,000-gas/0.05-ETH policy bounds remain mandatory before preparation and signing. These limits may reject otherwise valid high-cost Arbitrum transfers. See [Arbitrum gas estimation](https://docs.arbitrum.io/arbitrum-essentials/how-to-estimate-gas) and [OP Mainnet fees](https://docs.optimism.io/op-stack/transactions/fees).

## Durable intent, submission and reconciliation

A payment progresses through explicit preparation, durable signature, uncertain/acknowledged submission, inclusion and provider-observed finality. Execution success/failure is separate from inclusion/finality. The local journal commits exact signed bytes and locally calculated hash **before** a broadcast path may use them. A request-level storage success is insufficient: the full transaction must commit. A storage failure blocks broadcast.

Matching repeated intent/signature operations are idempotent. Conflicting preparation or signed bytes are rejected. Active nonce reservations include network and account. The browser serializes conflicting writes through IndexedDB transactions and verifies revisions; native SQLite uses immediate transactions and unique constraints. Neither platform allocates another nonce or signs another payment to work around an uncertain result.

Read failures are reported as unavailable reads, separately from uncertain submission. A broadcast follows one configured path and one attempt; a failed relay response never triggers an automatic direct broadcast. An explicit retry first reconciles and uses identical stored bytes. A timeout, HTTP/RPC error, missing receipt or dropped response after submission does not prove failure. Acknowledgement does not establish execution or finality. Retry uses only the exact already committed bytes; no fee replacement or on-chain cancellation is implemented. Late uncertain submission evidence cannot downgrade an acknowledged pending state. Only unsigned preparation can be cancelled locally.

Receipt validation checks the real signed transaction, hash, sender, actual contract/destination, type, status, gas charges, canonical block identity and bounded logs. Stablecoin success requires exactly the expected contract's transfer event with the intended sender, recipient and amount. Status success without that expected event remains unresolved. Canonical block is checked again after the finalized-head query to reduce an observation race.

A changed receipt is not permission to discard previous evidence. The client checks the **previous inclusion at its own stored height** first; only a proven noncanonical prior block triggers an explicit reorg correction. Prior observations remain in events. Conflicting receipt contents while the old block remains canonical fail closed. Contradiction of previously finalized evidence is flagged for investigation and does not authorize automatic rebroadcast or silent finality repair.

The core does not verify consensus or Merkle proofs. Same-provider repeated queries and the `finalized` tag are not independent confirmation. One dishonest provider can present a consistent false chain view, omit transactions or deny service. Fixed endpoints also create availability/rate-limit dependencies. TLS authenticates the endpoint, not the financial truth of its response. The application does not represent its local history as an authoritative blockchain ledger.

## Balances, audit and retained risks

Android's displayed USD values are separate from blockchain balances and transaction accounting. Coinbase receives fixed public currency-pair requests, without wallet addresses or holdings. RPC providers still receive public account queries; each network service can observe ordinary connection metadata. Quotes are stored separately from wallet secrets and carry the local receipt time, not an invented exchange timestamp. Quotes older than two minutes are stale, and those older than 24 hours or in the future are unavailable. Positive holdings with missing or stale prices, or stale balances, are never hidden by the USD small-balance filter. Exact decimal multiplication drives both totals and threshold comparison; rounded display values never enter the journal or signing request. A missing quote or balance produces an incomplete valuation, not an invented zero or stablecoin peg. Only known zero units can be valued at zero without a price.

Balances are observations at identified canonical blocks. They are not calculated from a local opening balance minus outgoing payments. Snapshots and payment evidence carry chain/account identity and exact units. Existing snapshots cannot silently be replaced with conflicting values at the same block; stale observations do not supersede newer ones. Browser projections are checked against their stored observations, and stored receipt observations are revalidated through the shared Rust validator.

### Incoming activity and bounded discovery

The activity view combines this installation's outgoing payment records with verified direct ETH and allowlisted-token transfers involving the account. Candidate hashes come from recent token logs, manually pasted hashes, and an optional history index where available. Indexer amounts and balance deltas never create transfer records. Web discovery scans at most 8,000 recent blocks in windows of at most 2,000 and verifies at most 24 candidates per refresh; it also checks at most eight recent full blocks for direct native ETH transfers. Android scans supported-token recipient logs and accepts manual hashes for direct ETH. Coverage is explicitly partial; internal ETH calls, older history and unsupported assets are not exhaustively indexed.

The shared Rust `validate_activity` checks transaction/receipt hash and participants, selected chain, canonical block identity and transaction membership when returned, execution status, fixed token contract, exact Transfer topics/data and log identity. Removed logs, malformed supported-token events and duplicate log indices are rejected. Zero-value events are omitted. A token mint from the zero address can still be an incoming transfer. A later receipt may not add, remove or change the recorded transfer set at an unchanged transaction/block identity. Native ETH observations require a successful top-level transaction value involving the address; internal-value tracing is outside this implementation. Finality remains a provider observation.

Incoming evidence has a separate additive journal. The browser keeps the original `local-wallet-mainnet-v02` database and vault store and adds activity stores with a version-2 schema upgrade. Android adds `activity-v1.sqlite3` without rewriting the encrypted vault or outgoing journals. Same observations are idempotent; earlier inclusions require an explicit canonical contradiction before re-inclusion. A contradiction involving a previously finalized observation remains an incident rather than automatically becoming a new confirmed deposit. Persisted activity on both platforms is revalidated against its stored proof before display. Repeated copies of proof evidence are limited to an aggregate 4 MiB per observation batch before persistence; oversized activity is reported as unavailable rather than silently truncated.

A missing receipt, partial scan or unavailable index does not establish that a deposit failed. A manual lookup distinguishes pending, not found on the selected network, reverted, unrelated, observed and unavailable results. Existing verified evidence is retained through later read failures. Balances remain independently observed on-chain state. Recovery words restore signing access, not deleted local evidence. Audit exports omit raw signed transaction bytes and all key material; they still expose addresses, counterparties, amounts and timing.

Other retained risks include malicious recipients, clipboard replacement, compromised display/input, issuer freezing/blacklisting or contract upgrades, network outages and reorganizations, phishing, supply-chain compromise and insufficient recovery backup. A software wallet cannot promise protection against a fully compromised endpoint. Neither this document nor the included automated checks replace an independent assessment and real-device/live-flow validation.
